## Getting around and first run

**A public home page and guides.** `/` is a short, single-column page for visitors: what the app is and one screenshot, "How it works" in three numbered steps, "What it never does", a second sign-up button and the common questions (collapsed; they also feed `FAQPage` structured data, alongside `SoftwareApplication`). Signed-in people are sent straight to Overview. `/guides` has three evergreen how-tos (export your LinkedIn connections, build a networking plan, track job applications), each with `HowTo` structured data. All of these are static and are listed in the sitemap and `llms.txt`.

**Signing in and signing up.** The sign-in page has **Sign in** and **Sign up** tabs. You can **continue with Google**, use an **email and password** (at least 8 characters; sign-up asks you to confirm your email; "Forgot password?" sends a reset link to a page where you choose a new one), or have an **emailed sign-in link** sent instead of using a password. A wrong password and an unknown email give the same message, and the reset email gives the same reply either way, so the form can't be used to find out who has an account. `/login?mode=signup` opens on the Sign up tab. After signing in you go to the page you were trying to reach. If Google isn't set up, the button returns to the sign-in page with a message instead of an error page (see [Deploying](DEPLOYMENT.md#google-sign-in)). Locally, emails are read in Mailpit.

**A short welcome, a tour and a checklist.** The first time someone signs in, a four-step welcome asks what they want to do (**network**, **jobs** or **both**), offers to set up job titles and places, and ends with one suggested first action for that goal. It can be skipped and reopened from **Help** or **Settings**. **Help → Take the tour** is an 18-stop walkthrough that visits each page in turn and points at what matters on it. Overview shows a **Getting started** checklist built from real records (a plan, a starting count, a search, a candidate, a resume, a saved job), so it can't drift from what has actually been done, and it can be dismissed. **Look around with example data** (step 2 of the welcome) fills an empty account with 30 made-up people, a plan, connection counts and 9 applications, all flagged `is_sample`; a banner on every page says so, **Clear sample data** removes exactly those rows, and they are never part of the data export. Progress is saved per account in `settings.onboarding`. If that can't be read (for example a deploy ahead of its migration), the app falls back to a fresh state, saves nothing and logs the reason; the tour never fails silently.

**Command palette and keyboard shortcuts.** Press **Ctrl+K** (or **Cmd+K**, or **/**) anywhere, or use the **Search** button in the top bar, to jump to any page, run common actions (add a candidate or job, import people, take the tour) and search your own candidates, people, applications and jobs by name. **g** then a letter goes to a page (**g a** Applications, **g s** Settings and so on) and **?** lists them all. Plain-key shortcuts never fire while you type in a field or while another dialog is open. The palette is downloaded the first time it is opened, so it adds nothing to a page's first load. Not built yet: `j`/`k` to move through lists and per-row keys.

**Canadian French and an i18n base.** Choose **English** or **Français (Canada)** from the picker on the sign-in page, in the top bar (and the phone menu), or in **Settings → Language**. The choice is kept in a cookie and in your account, so it follows you to other devices; before you choose, the browser's language is used (any French becomes Canadian French). **Translated today:** the menu and top bar, sign-in, sign-up and password reset (including server error messages), the welcome, the example-data and paused banners, and the search and shortcuts palette. **Still English:** every other page (Overview, Candidates, Jobs, Applications, Settings and so on), the public landing page, guides, Privacy Policy and Terms, the tour, emails, and dates, numbers and money on those pages. The base is a typed message file per language (`src/lib/i18n/messages`): the French file must have exactly the English keys or the build fails, and a test checks that every `{placeholder}` is kept and that nothing is left untranslated. Only the language in use is sent to the browser. To translate another page: move its text into the message files, read it with `useT()` (client) or `getT()` (server), and add the French.

**A menu that follows the goal.** Every page stays one click away, but only the ones that match the chosen goal are always on show:

| Goal | Always shown | Under **More** |
|---|---|---|
| Network | Overview, Discover, Daily Queue, Candidates, Follow-ups, People | Connections, Analytics, Disciplines, Schools, Jobs, Applications |
| Jobs | Overview, Jobs, Applications | Discover, Daily Queue, Candidates, Follow-ups, People, Connections, Analytics, Disciplines, Schools |
| Both (or not chosen) | Overview, Discover, Jobs, Daily Queue, Applications | Candidates, Follow-ups, People, Connections, Analytics, Disciplines, Schools |

Settings and Help are always visible, and the language picker is in the top bar (and the phone menu). **More** groups what's inside it (My network, Insights and so on) and opens by itself on one of its pages. On a phone the same list is a menu button that opens a side panel; the top bar stays in view while scrolling. The goal can be changed at any time by restarting the welcome.

## Your network

Nothing about your networking plan is built in. In **Settings → Your networking plan** you enter your own **schools** (with the other ways each is written, such as "UBC" or "U of T"), your own **disciplines** in priority order, a **connection goal**, a **starting count** and **start date**, and **targets** per discipline and per school. Schools can have their own targets, or be an extra pool that only counts toward a discipline's total. Candidates are sorted only into what you add.

**Candidates** are people you intend to invite, tracked from review to invitation to acceptance (new, awaiting review, approved, invitation sent or pending, connected; or declined, not a match, do not contact). People are de-duplicated by their profile link. Each has a school and a program, each marked **confirmed** or **needs review**; the app never guesses a school or program it can't read from the text.

**Quick capture** is the fast way in. On a LinkedIn people search, press Ctrl+A then Ctrl+C. In **Candidates → Quick capture**, press Ctrl+V:

1. Only what is on your clipboard is read, in your browser. Nothing is fetched from LinkedIn. Both the page's HTML and plain text are understood; links to profiles become people.
2. Each person's school and program are matched against **your** lists and their aliases, from the headline text. A program comes from the headline only, because "Past:" lines can mention other fields.
3. People already in your list, and people marked already connected, are left out. Rows missing a school or program are flagged ("Needs school") rather than guessed; you can set them per row, or fill every blank row at once.
4. **Add** saves everyone with both fields set. The checkbox "Approve the ones with school and program set" (or the **auto-approve** setting) controls whether they go straight to approved or wait for review. The cursor then returns to the paste box, so the next page is one Ctrl+V away.

The shortcut buttons above the paste box open the matching LinkedIn search for each school and discipline pair you still need people in, with how many are left to reach the target.

**Import** reads a CSV, or the connections file from LinkedIn's own data export, and can also fill your known connections and update everyone's status at once. Email addresses in imported files are never stored and the files are not kept.

**The Daily Queue** is the approved people to invite today, in the order of your discipline priorities and within your daily target. You open each profile, send the invitation yourself, and press **Mark sent**. A daily job (or **Run now**) classifies new candidates, marks older invitations as pending and rebuilds the queue. Suggested connection notes use only what you entered under **Settings → About you** and what is on the candidate's record, and nothing is invented. **Pause outreach** (Settings) stops the queue if LinkedIn shows a warning.

**People** is a small CRM for people worth meeting: status, notes, tags, reminders, referrals, and "people at this company". Discover results you save end up here. **Known connections** keeps the list of people you already know, so Discover leaves them out. On a phone, these lists are cards with a labelled line for each column.

**Bulk actions and saved views on Candidates.** Tick people (or the box in the header for the whole page) and a bar appears with **Approve**, **Needs review**, **Not a match**, **Do not contact** and **Delete…**. Each applies the same rules as the single-person action, skips anyone the rules refuse and says how many ("2 marked approved. 1 skipped."), and has **Undo** (it restores only people nobody has changed since). Delete asks first and cannot be undone. Up to 200 at a time. **Saved views** keep a set of filters under a name in your account (open one, save the current filters, delete); a view is just the page's URL, so links and the back button work, and the last filters used are restored on that device when you return. **Per page** offers 25, 50 or 100. Not built yet: the same bulk bar on People and Applications, and the card-mode "Select" on phones is the same checkbox on each card.

**Follow-ups after someone accepts.** When an invitation is accepted, the app suggests four touches: a thank-you (the day they accept), a short-chat ask (a week later) and check-ins at 30 and 90 days. **Follow-ups** lists what is due and what is coming, each with a draft you can edit and copy, **Done**, **Snooze a week** and **Dismiss** (all with Undo). Drafts come from fixed templates that use only the person's name and, if known, their school and field; if you edit one so it states something the record can't back up, copying it warns you. Nothing is sent for you. Overview shows "N follow-ups due", the bell announces them once a day (using the Reminders switch in Settings), and `g f` jumps there. A touch that was due more than a week before it was created is skipped, so importing old connections doesn't pile up stale tasks. Not built: an AI rewrite of the drafts.

## Network discovery (Discover)

**Discover** is a research assistant for finding people worth meeting, for example "Find 50 UofT Computer Engineering alumni working as software engineers". It is not a LinkedIn tool: it never visits, searches or automates LinkedIn.

1. **Connections**: import your Connections.csv (or any contact list) so people you already know are left out. The LinkedIn data export import on Candidates → Import fills this list too. Emails are never stored, and the file isn't kept.
2. **Understand**: the AI (Gemini by default) turns the request into structured criteria (school and its aliases, programs, roles, companies, places, count). A built-in parser does it without a key. ECE is never treated as Computer Engineering unless you say so.
3. **Plan and search**: many small, targeted searches (alumni, design teams, labs, personal sites, the school's own site, GitHub), deduplicated, each excluding LinkedIn. Sources: GitHub's and ORCID's public APIs (no key), plus Brave Search for the open web when configured, all behind a `SearchProvider` interface.
4. **Evidence**: pages that mention the school are read (respecting robots.txt; LinkedIn URLs are never fetched). The AI extracts people, and **every fact must quote the page**. The server checks each quote and link against the page and drops anything it can't find. Confidence (high, medium, low) comes from rules, not from the model.
5. **Verify**: the top 30 people are checked on their own pages, without AI: their GitHub profile README and social links, and the website they list. Each line that states their school, program, class year (including UofT's "2T4"), role or employer becomes a quoted fact. Two independent sources agreeing raise a fact to high confidence (never for ECE vs Computer Engineering), and an "alumni" request doesn't verify someone who is still studying.
6. **Resolve and dedupe**: the same person across sources is merged only with a corroborating signal (same GitHub, site, or name plus employer and school); otherwise they're flagged as a possible duplicate. People matching your known connections are hidden (≥ 95%) or shown for review (75–95%). Your answers are remembered.
7. **Rank and explain**: a transparent score (education 30, program 25, career 15, company 10, location 10, evidence 10) with a per-line breakdown, then an optional AI rerank that explains why each person is worth meeting, citing only verified facts.
8. **Act yourself**: every person has a LinkedIn button. **LinkedIn profile** opens the profile link the person published themselves (on GitHub, ORCID or their website). Otherwise **Find on LinkedIn** opens LinkedIn's people search for their name and employer or school; check it's the right person and paste their profile link in the drawer to keep it. Save people to **People**, track status, notes, tags and reminders, mark 2nd or 3rd degree if you checked LinkedIn yourself, copy a suggested intro, open their profile in a new tab, or send them to Candidates and the Daily Queue.

**No keys needed to start.** Without any API keys, Discover searches two free public sources whose data needs no AI to read: **GitHub** profiles (name, bio, company, location) and **ORCID** records (people's own education, with school, department, degree and years, and their employment, with employer and title). Requests are understood by a built-in parser, and matches are explained by their score breakdown. Working at a school is never counted as having studied there. Adding a free `GITHUB_TOKEN` (no permissions) raises GitHub's limit from about one search an hour. `BRAVE_SEARCH_API_KEY` and `GEMINI_API_KEY` (free) are optional upgrades: they add personal sites and team pages read by AI, and written explanations.

**Canada only.** Every search looks for people located in Canada. Location comes from evidence: a GitHub profile's location, the country on an ORCID record or the city of their current employer, "Based in Toronto" on their own page, or a web page. Someone shown to live elsewhere (for example "Seattle, WA") is left out and listed under "didn't qualify" with the reason. Someone whose location isn't public can't be verified and is shown as a possible match. Sources that disagree lower confidence. "Vancouver, WA" counts as the United States, and city names shared with other countries (London, Hamilton) only count with a province. Under **Modify**, a search can use another country, or none.

The research agent works in short, resumable steps with hard budgets (30 queries, 100 pages, 200 people, 60 AI calls per search). It stops when it has enough verified people, a budget runs out, or new searches stop finding new people. It returns fewer people rather than lowering the bar. Search results are cached for 3 days and pages for 14.

## Jobs

**Jobs** searches real, recent postings in any country and any field (tech, design, retail, sales, support, healthcare, finance, education…), checks each against your resume, and helps you apply: either by tailoring your resume with AI or with specific notes on what to change yourself. Trust comes first: **real > verified > relevant > recent > quantity**.

**Your country.** You search one country at a time (or **Anywhere (remote)**), chosen in the search bar or your preferences. A search shows jobs located there plus remote jobs open to it, to its world region (for example EMEA or Latin America) or to anyone. Canadian searches can also be narrowed by province; elsewhere, type a city or region. Every job records where it can be done: country codes, region tokens and "anywhere", read from the source's structured fields or its location text. A place that can't be read is never guessed, and "Remote" with no country is not assumed to be anywhere.

**Where jobs come from.** No paid job-data service and no job API key is needed.
1. **Employers' own job boards: the preferred, direct source.** A shared crawler reads the public job-board APIs behind employers' careers pages (Greenhouse, Lever, Ashby, SmartRecruiters, Workable, Recruitee, and Workday, which most large employers use) every 30 minutes to 6 hours, from a shared directory of employers (`supabase/seed/employers.json`, plus any added under **Jobs → Employers**). Boards list jobs worldwide; the crawler keeps only jobs open to a country some user searches, so storage grows with the countries people choose, not with every board's whole list. Choosing a country nobody searched before makes every board due for a fresh read, so its jobs appear within about 10 minutes.
2. **Jobicy** ([public jobs API](https://jobicy.com/jobs-rss-feed), free, no key): remote jobs in many fields. Each search asks Jobicy for your country's location (or its region when Jobicy has none, e.g. India → APAC), with your search words, and with Jobicy's industry when the words clearly name one ("UX designer" → Web, UI & UX Design; asked again without it if that finds nothing). It follows Jobicy's cursor for later pages, and each answer is reused for an hour, as Jobicy asks. Jobicy has no city or date filter, so its jobs are remote with no city, and the app filters them by date itself. Pay is shown only when Jobicy states it, in its own currency.
3. **Remotive** ([public API](https://github.com/remotive-com/remote-jobs-api), free, no key): remote jobs, kept when their required location covers a country someone searches (by name, region or "Worldwide"). Remotive asks for at most 4 reads a day, so the crawl job reads its feed at most every 6 hours and searches use the stored jobs. Remotive shares jobs 24 hours after it posts them, so its jobs never appear in the last-24-hours results.
4. **Arbeitnow** ([free job board API](https://www.arbeitnow.com/blog/job-board-api), no key): jobs in Germany, elsewhere in Europe and the UK, in many fields. Its API is a feed without search, so the crawl job reads its newest pages at most every 6 hours and keeps the jobs open to countries people search. Its terms ask for a link back to Arbeitnow, so every Arbeitnow job is credited and links to its Arbeitnow page.
5. **USAJOBS** (optional, [free key](https://developer.usajobs.gov/)): U.S. federal government jobs (nursing, administration, trades, science…), asked for searches in the United States when `USAJOBS_API_KEY` and `USAJOBS_EMAIL` are set. Each job links to its official announcement, and is ranked like an employer's own posting.
6. **Careerjet** (optional, [free publisher key](https://www.careerjet.com/partners/)): job search across 90+ countries, asked from the Jobs page when `CAREERJET_API_KEY` is set (it needs the searcher's IP and browser, so alerts don't ask it). Its links go to Careerjet's listing pages; descriptions are snippets, so fit on those jobs is marked partial.
7. **Adzuna** (optional): only when `ADZUNA_APP_ID` and `ADZUNA_APP_KEY` are set, and only for the countries its API covers. Nothing depends on it. Its estimated salaries are never shown; its descriptions are snippets, so fit on those jobs is marked partial.
8. **Postings you paste** (from LinkedIn, Indeed, Glassdoor or anywhere), private to you. Paste the whole job page (Ctrl+A, Ctrl+C) into **Quick fill** and the form fills itself from it (title, company, place, the posting text), read in your browser from what you pasted; every value is copied from the page and anything unclear is left for you. **Read with AI** (one AI use) suggests the same fields, and only values found word for word in the paste are kept.

Not used: **The Muse** (its terms would allow it, but its API has no keyword search, so results wouldn't match what you typed).

Jobicy and Remotive are credited on every job they supply ("Jobicy · a remote-jobs listing on Jobicy, not the employer's own page"), and their links go to their own listing pages exactly as their APIs give them: never a guessed employer, ATS or LinkedIn link. When the same job is on an employer's board too, it's shown once with the board's link, and "Also listed on Jobicy". A source that fails (timeout, rate limit, outage) never stops the others: you see "Some job sources are temporarily unavailable." and the rest of the results.

LinkedIn, Indeed, Glassdoor and Google Jobs aren't searched: they have no public job-search API, and the app doesn't scrape (nor have an AI read them for it, which is still scraping). Instead, under the search bar, **Also search on LinkedIn · Indeed · Glassdoor · Google Jobs** opens the same search on each site in a new tab (your words, country and city filled in); bring a good find back with **Paste a posting**. Workday has no public API either.

**Links are real and verified.** Every link comes from the source's own data, never from a pattern or a model. A job is **Verified** when its employer's board lists it in the latest read with a link that belongs to that board or employer, or (for Jobicy, Remotive, Adzuna and pasted jobs) when a live check finds the page. A Jobicy job is first checked with Jobicy's free status endpoint: "closed" marks it **Expired**, "unknown" leaves it **Not yet verified** (never verified), and only "active" goes on to the live check. In a live check, a 404 or "no longer accepting applications" page marks it **Expired**; a site that blocks automated checks leaves it **Not yet verified**, never "failed". Live checks follow redirects by hand and refuse any URL or redirect that resolves to a private or reserved address (`src/lib/net/safe-fetch.ts`). **Apply works only for verified listings.** Searches show verified listings by default; unverified ones can be included, with Apply off. Expired jobs stay in your saved list with Apply disabled.

**Searching.** Search by keyword, country and place. Close variants of a title are included, in any field ("Full Stack Developer" also finds "Full-Stack Engineer"; "UX Designer" finds "Product Designer"; "Retail Associate" finds "Sales Associate" and "Cashier"; "Customer Service Representative" finds "Customer Support Specialist"), broader ones rank lower. Seniority words ("Junior", "Senior") aren't required in titles, since most postings don't say them; the level filter handles seniority. "Software development" is read as the developer role. With no date chosen, the search starts at 24 hours and widens to 3 days, then 7, when there are fewer than 10 verified results, and says so. Filters: workplace (remote, hybrid, on-site), level, employment type, salary (the minimum compares only pay stated in your country's currency; nothing is converted), company and source, each matching only what a source actually states (no visa filter: no source states it reliably). The same job from several sources is shown once, with the most direct link. Results are ranked by fit (40), title (25), recency (15), location (10) and source quality (10), 25 per page.

**Fit, explained.** Each requirement line is matched against your resume by a skills list with aliases (technical skills, plus design tools and UX methods, office tools, retail and customer service, sales, marketing, accounting, HR, project management, health and safety certifications, hospitality, logistics, teaching and spoken languages) and (with `EMBED_SECRET`) by meaning; every "met" quotes a real line. Rules decide years, degree, clearance and work authorization (in the country you search). Cards say why: "Strong matches: React, TypeScript · Missing: AWS · Preferred not found: 3+ years".

**Your resume.** Import a PDF, a Word document (DOCX) or pasted text. It's read without AI (optionally with a second AI read) into contact details, LinkedIn/GitHub/portfolio links, summary, skills (grouped into languages, frameworks, libraries and tools), experience, projects, education (school, degree, major, graduation), certifications, awards and activities. Every field carries a confidence: uncertain ones are filled but marked **Needs review** with the reason ("We found multiple possible dates"), unclear ones are left empty with the candidate offered, and missing ones say "Not found in your resume". A summary shows how many fields were filled, which need attention and how complete the profile is. The **original** (file and text) is kept unchanged and can be downloaded; the parsed original can be restored; every tailored version is kept and can be compared, edited or deleted (with Undo).

**Two ways to improve your resume for a job.**
- **Tailor Resume** (or **Tailor CV**): AI rewrites a new copy for the job. An accuracy check removes anything your resume doesn't support (new skills, employers, numbers), and a materiality check makes sure the result really is more specific than the original. If it isn't after one retry, nothing is saved and you get Improvement Notes instead. A comparison shows keyword match and requirement match before and after (computed the same way for both), what changed and which requirements are missing.
- **Get Resume Improvement Notes**: advice only. Your resume isn't changed. Notes are grouped by section, prioritized (high, medium, optional), each with why it matters, plus a comparison of strong matches, terms that could be emphasized, and requirements not found ("Do not add it unless you genuinely have that experience").

Without AI (no key, or today's free uses spent), **Tailor Resume doesn't fake it**: it says AI rewriting is unavailable and gives Improvement Notes, with links to add your own key or try later. A deterministic reordering is never labelled "AI Tailored". **Cover letters** are written by AI (checked sentence by sentence), or filled from a template that's labelled as one. Every document can be edited, regenerated and downloaded as PDF or Word.

**AI is Google's Gemini by default**, through the official Gemini Developer API, which has a free tier (`GEMINI_API_KEY`; model in `GEMINI_MODEL`, default `gemini-3.8-flash`). It runs on your own key (Settings, stored encrypted) or the app's key with no limit (set `AI_DAILY_QUOTA` to cap uses per user per day). Every call asks for structured output and validates it; a malformed answer is rejected, never partly used. The AI sits behind a provider interface (`src/lib/ai/provider.ts`, implemented once in `src/lib/ai/llm-ai-provider.ts` over any model service). Anthropic Claude still works as an optional alternative (`ANTHROPIC_API_KEY`, or a user's own `sk-ant-…` key) but is never required. Match scores are always computed by rules, never by a model.

**AI and your data.** AI is optional; everything except the AI rewrite itself works without it. When it's used, your resume text and the job posting are sent to the AI service (Google, for Gemini). On Gemini's **free tier, Google may use what you send to improve its products** (see Google's [Gemini API terms](https://ai.google.dev/gemini-api/terms)); on its paid tier it says it doesn't. Don't add a key if you don't want that. Keys never reach the browser: `npm run check:bundle` checks the built client files after `npm run build`.

**Limitations.** Coverage depends on the employer directory: it started with tech employers, and non-tech and non-Canadian employers are added through `scripts/employer-candidates-worldwide.txt` and **Jobs → Employers**. Large retailers and many big employers use Workday or similar systems that have no public API, so in-store retail jobs stay thin (the app doesn't scrape). Jobicy and Remotive only list remote jobs. Jobicy can't filter by city, so a city search narrows only employer boards. Remotive's jobs arrive a day late. Gemini's free tier has daily request limits; when they're used up, Tailor Resume gives Improvement Notes. Links on job sites that block automated checks stay **Not yet verified**.

Also: Saved / Applied / Not interested (each with Undo), and **Find people at {company}** in Discover. Feedback is announced with toasts (`src/components/toast/`): readable, dismissible, announced to screen readers, longer for errors and warnings, and F6 moves focus to them.

## Applications

**Applications** tracks every job you pursue from **saved** to **offer**, on a board (one column per stage, one column on a phone) or a sortable list. Stages: saved, applied, screening, interviewing, offer, accepted, rejected, withdrawn, no response. Nothing moves on its own.

- **One row per attempt.** It keeps a copy of the posting, so the application survives the job being removed. There is at most one open attempt per job; **Apply again** starts a new one.
- **Save, I applied and remove** on the Jobs page keep the tracker in step. A job you dismiss never creates an application. After you follow a verified **Apply** link, the app asks **"Mark as applied?"**; it never assumes you did.
- **Every move is kept on a timeline** (stage changes, notes, responses, interviews, reminders, contacts and documents). A version check stops two open tabs from silently overwriting each other.
- **Interviews** have a time and zone. A changed time asks you to confirm. Each interview downloads as an **`.ics`** calendar file (UTC, stable id, updated sequence number).
- **Reminders**, **contacts** (people you know there, with their role, linked to People), **documents** (an unchangeable copy of a resume or cover letter used) and **offered pay** (entered by you, never converted or estimated).
- **No response** is only ever suggested, after the number of days you set in **Settings → Applications**.
- **Referrals.** On a company page or a person's record, record "I asked" or "They referred me". An optional draft message is a template, or an AI rewrite that is checked so it doesn't say anyone works there now, invent facts or imply a meeting that wasn't recorded. It is copied, never sent.
- **Company pages** (`/companies/<name>`) gather the applications, verified open jobs, referrals and the people you know at a company. Matching company names is careful: an exact name (after legal suffixes like "Inc.") counts; regional names, brand groups (Amazon and AWS) and prefixes are only **possible**, and your "same / different company" answers are remembered and can be undone.

**Interview prep for each application.** An application in Screening, Interviewing or Offer (or with any interview booked) has an **Interview prep** button. The pack is built live, only from your saved posting, your own resume and your booked interviews: **likely topics** (the posting's requirements, required ones first), **questions they are likely to ask** with your own resume lines matched by simple word rules and shown with where each came from, **one question per required skill** (and a plain "no line in your resume mentions this, be honest about the gap" when nothing fits), **questions to ask them**, a **checklist for the day** that uses your next interview's time in its own time zone, and **sources**. It says nothing about the company: the only link is the posting you saved, and a note tells you to read the company's own site yourself. **Copy as Markdown**, **Download** and **Save to timeline** (a saved copy appears on the application's timeline). No AI is involved, so it cannot claim experience you did not record. Not built: an optional AI rewrite of your stories, and company facts with sources.

## Alerts and notifications

- **Saved searches** (up to 20) re-run on the schedule you choose, **daily or weekly at your local hour**, correct across daylight-saving changes. What a search shows when you save it is the baseline and is never announced; a job counts as new only when no copy of it, from any source, was seen before.
- Alerts read **stored jobs only**, so they never call an outside source. Overlapping runs can't announce anything twice, and a failed run is retried without losing its matches.
- **Notifications** (the bell, with an unread count) also cover reminders that are due, interviews in the next 24 hours (announced again if one moves), a Monday summary of your search, job boards you added that stopped working, and a daily "N follow-ups due" note (the same Reminders switch in Settings controls it). Mark one or all as read, with **Undo**. Read notifications are deleted after 90 days.
- **Email digests** are optional and opt-in twice (in Settings and on each search). They contain job titles, companies and links only, no tracking, and every email has a one-click unsubscribe. They switch on only when the server has SMTP configured (see [Deploying](DEPLOYMENT.md)); otherwise alerts stay in the app.

## Progress and analytics

- **Overview** leads with **one recommended next action** (for example "Send invitations, starting with Computer Science", "Review 3 candidates", or "Set up your networking plan"; a LinkedIn warning always comes first), then your network total against your goal, a job-search summary (reminders and interviews due) and a folded **Detailed breakdown** (pipeline, activity and each discipline against its target).
- **Only accepted invitations count toward a target**, and only when the person's school and program are confirmed. **Pending invitations are shown apart** (a hatched segment) and never counted. The counting rules live in `src/lib/progress/` and are unit-tested.
- The **network total** comes from counts you record or import, and says so. It can differ from tracked acceptances because it also includes people who invited you and connections you didn't log here.
- **Analytics** shows the acceptance rate (accepted divided by accepted plus declined plus withdrawn; pending is left out because its outcome isn't known yet), invitations sent and connections accepted over 30 days, weekly activity, and your recorded network total over time. Charts load as they scroll into view and each has a table version. **Disciplines** and **Schools** show progress for each.
- Nothing is estimated or invented: every number is built from what you recorded or imported.

## Look, phones and speed

- **Appearance** (Settings): theme **System, Light or Dark**, density, and text size, saved to your account and applied before the first paint, so there's no flash. Both themes keep every text and form-field colour pair at or above WCAG contrast (a unit test checks them), and reduced-motion settings are respected.
- **Built on shadcn/ui** (Base UI), with a refined neutral and blue look.
- **Phones.** The menu is a button that opens a side panel. Lists (People, Candidates, Connections, Employers) become **cards** with a labelled line for each column. The Jobs filters sit behind a **Filters (n)** button under the search box. Buttons and inputs are larger on touch screens, text fields use 16 px so iOS doesn't zoom, dropdowns open the phone's own picker (on a desktop they are the shadcn Select), the welcome appears as a bottom sheet, and the layout respects notches and the home indicator. Nothing is cut off at 360 px wide on any page (an end-to-end test checks 19 pages).
- **Speed.** Each page streams: the outline paints first and the data fills in. The charts library, the desktop dropdown, the job menu, the phone menu panel, the welcome, the tour, the toast interface and the search palette are downloaded only when first needed (only the language in use is sent, too), so a first page load is about 500-590 KB of JavaScript. `npm run check:budget` fails the build if a route grows more than 5% over `scripts/route-budgets.json`. Pages and the database sit in the same region, and each request reads settings once.
- **Monitoring.** Each browser reports Core Web Vitals (LCP, INP, CLS, FCP, TTFB) and errors to `/api/vitals` and `/api/client-errors`; server errors are recorded by `src/instrumentation.ts`. Only the route pattern (`/applications/[id]`, never an id), the number, a phone/desktop flag and a scrubbed error message are stored: no user id, IP address, cookie or page content, and email addresses, keys, links, ids and profile addresses are removed from messages on the server. Nothing is sent if the browser says Do Not Track. Data is deleted after 30 days (measurements) and 90 days (errors) by the daily job. Operators run `CRON_SECRET=... npm run ops:report -- https://<app>` to see the 75th percentile per route and device and the recent distinct errors. No third-party processor is involved, so the Privacy Policy only gains a plain-language section. Not built: a web dashboard (the report is a script and JSON route), alerting when an error first appears, and Vercel Speed Insights (it can be added later; it would need a line in the policy).
- **Search and agents.** `robots.txt` allows crawling; the public pages (home, guides, sign-in, privacy, terms) are in the sitemap, with `llms.txt` and `/.well-known/ai-catalog.json` describing them. Everything behind sign-in redirects signed-out visitors, bots included, to the sign-in page.
